## 1. 서비스를 두 기능으로 정의

| | 기능 1. 내 업무 기억 | 기능 2. 인수인계 |
|---|---|---|
| 한 줄 | 내 업무를 **과정까지** 기록하고 저장한다 | 쌓인 기록으로 인수인계를 **쉽게** 한다 |
| 쓰는 때 | 매일 | 이동 전 / 인수 후 |
| 카드 | **업무 기록 카드** (`kind=work`) | **인수인계 카드** (`kind=handover`) |
| 핵심 관계 | 인수인계 카드는 업무 기록 카드에서 만들어진다 (`source_card_ids`) | |
| 판단 (공통) | 계획 비교, 질문하기가 **두 종류의 카드를 함께** 검색한다 | |

### 사이드바 (확정)

```
홈          대시보드
내 업무      기록하기 · 카드 덱 · 자료
판단        계획 비교 · 질문하기
인수인계     기록하기(인수인계 쓰기)[인계자] · 점검[인계자] · 카드 덱 · 자료 · 확인 모드[후임자]
```

- 인수인계 그룹은 상단 역할 전환(인계자/후임자)에 맞춰 해당 역할의 메뉴만 보인다.
- 사이드바 메뉴명은 짧게, 화면 제목은 풀네임("내 업무 기록하기" / "인수인계 쓰기").

## 2. 기능 상세

### 2-1. 내 업무 (기능 1)

| 메뉴 | 사용자가 하는 일 | 시스템이 하는 일 |
|---|---|---|
| **기록하기** | 업무 대화·메모를 붙여넣고, 관련 파일을 함께 올림 | Extractor가 **결정 + 과정**을 추출 → State Linker가 기존 카드와의 번복·대체 관계 판단 → Confidence Gate가 확신 낮은 카드에 "확인 필요" 표시 |
| **카드 덱** | 내 카드를 상태·주제로 보고, 카드 상세에서 과정을 확인하고 수정 | 카드 상세에 근거 원문, 버린 대안, 대체 관계, **과정 타임라인** |
| **자료** | 내 카드에 연결된 파일 모아 보기 | 연결 안 된 파일 표시 |

**업무 기록 카드의 "과정"** (결정 카드에 더하는 필드)

| 필드 | 내용 |
|---|---|
| `process` | 시간순 단계 목록. 각 단계는 `type`(시도 / 실패 / 막힘 / 결정 / 번복), `text`, `evidence`(원문 위치) |
| 기존 필드 | 결정, 근거, 버린 대안, 상태, 담당자, 날짜, 확신도, 첨부 자료 |

> 범위 결정(TODO: 추후결정): "과정"을 결정 카드에 붙은 타임라인까지로 할지, 하루 업무 일지 전체로 넓힐지. 현재 가정은 **타임라인까지**.

### 2-2. 인수인계 (기능 2)

| 메뉴 | 역할 | 사용자가 하는 일 | 시스템이 하는 일 |
|---|---|---|---|
| **기록하기 (쓰기)** | 인계자 | 인계할 범위(프로젝트·기간)를 고르고 초안을 다듬음. 인수자 메모 추가 | **Handover Drafter**가 내 업무 카드에서 인수인계 카드 초안을 만들고 각 문장에 원본 카드를 연결 |
| **점검** | 인계자 | "점검" 누르기 | **Gap Auditor**가 내 업무 카드 중 인수인계 카드에 반영되지 않은 것(빈 자리), 내용이 다른 것(불일치), 연결 안 된 자료를 찾음. 완성도 게이지 |
| **카드 덱** | 공통 | 인수인계 카드를 보고, 필요하면 연결된 업무 기록(과정)으로 내려감 | 후임자에게는 인계자가 **공개를 허용한 범위**만 보임 |
| **자료** | 공통 | 인계 자료 보기 | |
| **확인 모드** | 후임자 | 카드를 한 장씩 넘기며 "이해함 / 질문 있음" | **Question Drafter**가 질문 목록을 인계자용으로 정리 |

### 2-3. 판단 (공통)

| 메뉴 | 내용 |
|---|---|
| **계획 비교** | 하려는 일을 입력하면 두 종류의 카드에서 근거를 찾아 판정 배지(일치 / 충돌 / 기각된 안 / 관련 없음). 결과 카드에 **"내 기록" / "인수인계" 라벨**. 범위는 기본 전체, 선택으로 좁힘 |
| **질문하기** | "이 결정은 왜 했지?"에 카드와 원문을 근거로 답변, 근거가 없으면 "기록에 없음" |

### 2-4. 사용 흐름

| 시점 | 사람 | 하는 일 |
|---|---|---|
| 평소 | 나 | 내 업무 > 기록하기 (로그 + 파일) → 업무 기록 카드 |
| 평소 | 나 | 계획 비교로 같은 시행착오 방지, 질문하기로 "내가 왜 그랬지" 확인 |
| 이동 전 | 인계자 | 인수인계 > 쓰기: AI 초안 → 다듬기 → 점검 → 보강 → 인계 완료 |
| 인수 후 | 후임자 | 인수인계 카드 확인 모드, 막히면 연결된 업무 기록(과정)으로 내려감, 계획 비교 |
| 인수 후 | 후임자 | 자기 업무를 내 업무에 기록 → 다음 인수인계의 재료 |

## 3. 데이터 모델 변경

| 항목 | 변경 |
|---|---|
| 카드 | `kind`(work / handover), `source_card_ids`(handover에서 원본 work 카드), `process`(work의 타임라인), `shared_for_handover`(공개 허용 여부, TODO: 추후결정) |
| 카드 간 관계 | `card_links`에 `derived_from`(인수인계 카드 → 업무 카드) 추가. 기존 `supersedes`와 구분 |
| 인수인계 묶음 | `handovers`(인계자, 후임자, 범위, 상태, 인수자 메모), `handover_reviews`(카드별 이해함 / 질문 있음) |
| 프로젝트 | 카드의 속성 (선택 화면 없음). 이름표로 표시 |
| 스키마 소유 | `memory`: 카드·벡터·판정 (Agent만 쓰기). `app`: 사용자·인수인계 묶음·확인 표시·파일 (Backend만 쓰기) |

> 계약(`contracts/`)을 구현보다 먼저 고친다: 카드 스키마, 기록 API(과정 포함), 인수인계 초안 API, 판정 요청의 `scope`.

## 4. 에이전트 (LangGraph)

| 흐름 | 에이전트 | 변경 |
|---|---|---|
| 총괄 | Supervisor | 라우팅 종류: 업무 기록 / **인수인계 초안** / 판정 / 점검 / 확인 / 질의 |
| 업무 기록 | Extractor → State Linker → Confidence Gate | Extractor 출력에 **과정 단계** 추가 |
| **인수인계 초안** | **Handover Drafter → Verifier** | **신규.** 업무 카드를 인수인계 카드로 정리. Verifier가 "초안의 모든 문장이 원본 카드에 근거하는지" 확인 |
| 판정 | Intent Parser → Retriever/Reranker → Judge → Verifier | 두 종류 카드 모두 검색, 결과에 `kind` 표시 |
| 점검 | Gap Auditor | "양식"이 아니라 **업무 카드 vs 인수인계 카드**를 비교 (기존보다 단순해짐) |
| 확인 | Question Drafter | 변경 없음 |
| 질의 | Grounded QA | 두 종류 카드 모두, 근거 없으면 거부 |

## 5. LLM 적용

| 작업 | 모델 | 비고 |
|---|---|---|
| 결정·과정 추출 | 파인튜닝 소형 LLM (비교군: Sonnet 5.5 zero-shot, Haiku 5.5, BERT) | 과정 단계의 `type` 분류까지 학습 대상. 라벨 정의가 늘어 평가셋 주석이 늘어남 |
| 판정 | 파인튜닝 소형 LLM + Sonnet 5.5 설명 생성 | 판정은 기존과 같음 |
| **인수인계 초안 생성** | Sonnet 5.5 | 생성 품질이 중요한 작업. 구조화 출력(각 문장에 `source_card_ids`) 강제 |
| 초안 검증, 판정 검증 | Sonnet 5.5 (또는 다른 계열) | 생성 모델과 같은 계열이면 편향 가능 → 평가 심사는 다른 계열 |
| 단계 분류·질의 재작성 | Haiku 5.5 | 호출 많은 보조 작업 |

- 모든 호출은 LLM Gateway를 거치고(라우팅·재시도·JSON 스키마 강제·캐시·호출 기록), 테스트는 `LLM_FAKE=true`.
- 프롬프트와 판정 규칙은 `packs/work/`에서 로드. 인수인계 초안 규칙도 같은 위치.

## 6. RAG 적용

| 항목 | 설계 |
|---|---|
| 색인 대상 | ① 카드(필드별) ② 원문 로그 청크 ③ **과정 단계**(시도·실패 문장) ④ (확장) 파일 내용 |
| 인덱스 | **하나의 인덱스 + 메타데이터 필터** (`kind`, `status`, `owner`, `project_id`, `source_type`) |
| 검색 범위 | 계획 비교·질문: 기본 `kind` 전체. 인수인계 화면: `kind=handover`. 내 업무 화면: `kind=work` |
| 접근 제한 | 다른 사람의 업무 카드는 `shared_for_handover`가 허용된 경우에만 검색 대상 (필터를 검색 쿼리 단계에서 적용, 결과를 가린 뒤 거르지 않음) |
| 이웃 확장 | `card_links`를 따라 확장. 인수인계 카드가 검색되면 `derived_from` 원본 업무 카드를 함께 가져와 **"왜"를 근거로 제시** |
| 폐기·대체 카드 | 기존과 같이 검색 대상에 포함 (기각된 안을 찾기 위해) |
| 과정 단계를 따로 색인하는 이유 | 실패·시도 문장이 "기각된 안"을 가장 직접적으로 담고 있어 재현율에 유리할 것으로 **가정** → 실험으로 검증(R4에 "과정 단계 포함 여부" 비교 추가) |
| 파이프라인 | 질의 재작성 → 하이브리드 검색 → 리랭크 → 근거 묶기 → 생성·인용 검증 → 거부 (기존 6단계 유지) |
| 청킹 실험 | R1~R4 유지. 구조 기반 청킹에 "업무 기록 과정 단위" 후보 추가 |

### 같은 근거가 두 종류로 있을 때 (TODO: 추후결정)
같은 결정이 업무 카드와 인수인계 카드에 모두 있으면 결과가 중복된다. 후보: ① 인수인계 카드를 우선 표시하고 원본을 접어서 연결 ② 둘 다 표시하고 라벨 구분. 현재 가정은 ①.

## 7. 평가 (추가·변경)

| 지표 | 내용 |
|---|---|

## 8. 기술 스택

새 기술은 필요 없고, 기존 스택에 역할만 늘어납니다.

| 계층 | 기술 | 이번 변경에서의 역할 |
|---|---|---|

| Model Server | vLLM, Transformers + PEFT(QLoRA) | 추출 모델 파인튜닝 대상에 과정 단계 포함 |
| DB | PostgreSQL + pgvector (Chroma는 RAG Lab) | 카드 `kind`·`process`, `handovers`, `handover_reviews`, `derived_from` 링크 |
| 임베딩·리랭크 | BGE-M3 계열 3종 비교, bge-reranker-v2-m3 | 변경 없음 |
| 평가 | ragas, LLM-as-judge(다른 계열), 직접 구현 지표 | 초안 충실도·누락률·Gap 재현율 지표 추가 |
| 인프라 | Docker Compose, GitHub Actions | 변경 없음 |

## 9. 범위 등급 조정 (제안)

| 등급 | 항목 |
|---|---|
| **[필수]** | 내 업무 기록(결정 + 과정) → 카드, 계획 비교(장면 ①) + 판정 모델, 인수인계 초안 생성(Handover Drafter), 평가 실험표, 배포 링크 |
| **[선택]** | 점검(Gap Auditor) 고도화·완성도 게이지, 확인 모드, 질문하기, 후임자용 공개 범위 설정 UI |
| **[이후]** | 슬랙 실시간 연동, 권한 관리, 전사 통합 검색, 파일 내용 검색 |

인수인계 초안 생성을 [필수]에 넣는 이유: 두 기능을 잇는 연결 고리라서, 빠지면 "기록 서비스"와 "인수인계 서비스"가 따로 노는 것으로 보입니다.

## 10. 일정 영향 (제안)

| 영향 | 내용 |
|---|---|
| 늘어나는 것 | 과정 필드 평가셋 주석, Handover Drafter 구현과 평가, 사이드바·화면 이름 정리 |
| 줄어드는 것 | Gap Auditor가 "양식" 없이 카드끼리 비교하므로 인수인계 양식 입력 화면이 단순해짐 |
| 먼저 할 것 | 계약(`contracts/`) 카드 스키마 변경 → 예시 데이터에 `kind`·`process`·`source_card_ids` 추가 → 프론트 목업 |
| 정해야 할 것 | (1) 과정의 범위 (2) 후임자의 업무 기록 열람 허용 방식 (3) 중복 결과 처리 방식 |
