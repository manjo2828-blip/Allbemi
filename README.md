# Allbemi (올빼미) 기획서

> **모든(All) 업무 기록의 이유를 품는 올빼미.**
> Allbemi는 두 가지 일을 합니다. **① 내 업무를 과정까지 기록·저장**하고, **② 그 기록으로 인수인계를 쉽게** 합니다.
> 업무 대화·메모에서 **결정 카드**(결정 · 근거 · 버린 대안 · 과정 · 상태)를 자동으로 만들고, 새 계획을 입력하면 기존 결정과 나란히 비교해 **일치 / 충돌 / 기각된 안**을 판정하며, 인수인계 때는 쌓인 업무 기록에서 **인수인계 카드 초안**을 만들고 빠진 결정을 찾아 주는 **LLM · RAG 기반 멀티 에이전트 서비스**.

> 상태: **기획 단계 (폴더 구조 기본 틀 + 프론트엔드 목업 진행 중)**. 코드는 주차별로 채웁니다. 세부 설계 논의는 [`docs/두기능_설계안.md`](docs/두기능_설계안.md)에 있습니다.

## 1. 서비스 개요

| 항목 | 내용 |
|---|---|
| **서비스명** | **Allbemi** (All + 올빼미). 모든(All) 업무 기록의 이유를 품는 올빼미 |
| **한 줄 정의** | 내 업무를 결정과 과정까지 기록해 두고, 그 기록으로 인수인계를 쉽게 하며, 새 계획이 과거 결정과 충돌하거나 이미 기각된 안인지 먼저 알려 주는 서비스 |
| **두 가지 기능** | **기능 1. 내 업무 기억**: 내 업무를 과정까지 정확하게 기록·저장<br>**기능 2. 인수인계**: 쌓인 기록에서 인수인계 카드를 만들고 점검·확인 |
| **두 기능의 관계** | **인수인계 카드는 업무 기록 카드에서 만들어집니다.** 인수인계를 새로 쓰지 않아도 되고, 기록이 없으면 인수인계도 약해지므로 서로를 필요로 합니다. 판단 기능(계획 비교·질문)은 두 종류의 카드를 함께 검색합니다 |
| **차별점** | 기존 AI 검색은 무엇을 물어야 할지 알아야 답이 나오지만, Allbemi는 **하려는 일을 입력하면 과거에 기각된 안인지 먼저 알려 줍니다.** |
| **화면 원칙** | **카드가 화면의 중심이고, 채팅창이 중심이 아닙니다.** 질문 기능은 카드 화면 안의 보조 도구입니다. |
| **기술 중심** | **LLM**(역할별 모델 분리, LLM Gateway, 소형 LLM 파인튜닝)과 **RAG**(하이브리드 검색, 청킹 비교 실험, parent-child, 인용 검증)가 서비스의 핵심 |
| **프로젝트 성격** | 개인 프로젝트, 1인 6주(약 1달 반), LLM 엔지니어 취업 포트폴리오 목적 |

## 2. 해결할 문제

문제는 두 층입니다. **평소에 업무의 과정이 남지 않고**, 그래서 **인수인계에서 "결과"만 전달되고 "이유"는 사라집니다.**

### 기능 1이 푸는 문제 (내 업무 기억)

| 문제 | 설명 |
|---|---|
| 과정이 남지 않음 | 업무를 하며 시도하고 실패하고 버린 것들은 슬랙, 회의, 머릿속에만 있다가 사라짐. 결과물만 남음 |
| 같은 시행착오 반복 | 내가 이미 기각한 안을 몇 달 뒤 잊고 다시 꺼냄. 후임자나 새 팀원은 더 모름 |
| 몰아 쓰기의 한계 | 나중에 몰아서 정리하면 몇 달 전 결정의 이유를 잊고 일부를 빠뜨림 |
| 기존 도구의 한계 | 결정 기록 도구는 직접 등록해야 해서 바쁘면 중단되고, AI 챗봇은 무엇을 물어야 할지 알아야 하며 기각된 안을 먼저 알려 주지 않음 |
| 자료와 이유가 따로 놂 | 업무 자료 파일(수업 자료, 발표 자료 등)은 폴더에, 그 자료를 왜 그렇게 만들었는지는 대화에 흩어져 있음 |

### 기능 2가 푸는 문제 (인수인계)

| 문제 | 설명 |
|---|---|
| 이유 없는 인수인계 | 문서에는 "무엇을 쓰는지"만 있고 "왜 정했는지, 어떤 대안을 버렸는지"는 빠짐 |
| 인수인계가 별도의 큰 일 | 이동 직전에 처음부터 문서를 쓰느라 시간이 들고 빠뜨림 |
| 빠진 줄 모름 | 무엇이 빠졌는지 인계자 본인도 알기 어려움 |
| 후임자의 불안 | 어떤 결정이 왜 내려졌는지 모르고, 모르고 한 제안이 이미 기각된 안일까 불안함 |

공통: 자동 생성 결과는 틀릴 수 있어서 **확신도 표시와 사람 확인 단계**가 필요합니다.

### 페르소나

| 구분 | 인물 | 상황과 목표 |
|---|---|---|
| **인계자** (기능 1 + 2) | 박민준, 31세 백엔드 개발자 | 평소 슬랙과 짧은 메모로 소통하고 별도 문서는 미루는 편. 부담 없이 기록하고, 다음 달 다른 프로젝트로 이동할 때 빠짐없이 이유까지 넘기고 싶음 |
| **후임자** (기능 2 + 1) | 이서연, 27세 개발자 | 프로젝트를 처음 이어받아 인수인계 카드를 읽고 이해해야 함. 인수받은 뒤에는 자기 업무를 기록하고, 이것이 다음 인수인계의 재료가 됨 |

## 3. 주요 기능

### 3-1. 카드의 두 종류

| | **업무 기록 카드** (`kind=work`) | **인수인계 카드** (`kind=handover`) |
|---|---|---|
| 쓰는 때 | 평소 (자동 생성) | 이동 전 (업무 기록 카드에서 초안 생성 후 다듬음) |
| 성격 | 과정까지 있는 그대로의 기록 | 읽는 사람을 위해 다듬은 결과와 주의점 |
| 연결 | | `source_card_ids`로 원본 업무 기록 카드를 가리킴 |

**카드 한 장의 구성 (공통)**
- 결정 내용, 근거, **검토 후 버린 대안**, 담당자, 날짜, 프로젝트 이름표
- **상태**: 현재 유효 / 폐기 / 새 결정으로 대체
- **원문 보기**: 근거가 된 실제 대화·메모를 펼쳐서 확인
- **확신도 표시**: 불확실하면 "확인 필요"
- **첨부 자료**: 카드에 연결된 파일(예: 수업 자료, 발표 자료). 카드에서 미리보기·다운로드
- 업무 기록 카드에만 있는 **과정 타임라인**: 시도 → 실패 → 막힘 → 결정 → 번복의 시간순 단계 (각 단계에 원문 위치)

프로젝트는 화면에서 고르는 단위가 아니라 **카드가 가진 속성**입니다. 별도의 프로젝트 선택 없이 카드마다 이름표로 표시합니다.

### 3-2. 기능 1: 내 업무 기억 (기록·저장)

| 기능 | 내용 |
|---|---|
| **업무 기록하기** | 업무 대화·메모를 자유 형식으로 붙여넣으면 **결정과 과정**이 담긴 카드가 자동 생성 (형식 불필요). 같은 화면에서 관련 파일도 함께 올림 |
| **내 카드 덱** | 내 카드를 상태·주제별로 보고 시간순 정렬. 카드 상세에서 근거 원문, 버린 대안, 대체 관계, **과정 타임라인** 확인 |
| **카드 확인·수정** | 자동 생성된 카드를 고침. 자신 없는 카드는 "확인 필요" |
| **내 자료** | 내 카드에 연결된 파일 모아 보기, 연결 안 된 파일 찾기 |
| 계획 비교 · 질문하기 | 3-4 참고 (두 기능이 함께 씀) |

### 3-3. 기능 2: 인수인계

| 기능 | 사용자 | 내용 |
|---|---|---|
| **인수인계 쓰기** | 인계자 | 인계할 범위를 고르면 **Handover Drafter**가 내 업무 기록 카드에서 인수인계 카드 **초안**을 만들고, 각 문장에 원본 카드를 연결. 인계자가 다듬고 인수자 메모를 추가 |
| **인수인계 점검** | 인계자 | "점검"을 누르면 업무 기록 카드 중 인수인계 카드에 반영되지 않은 것은 **빈 자리**로, 내용이 다르면 두 카드를 나란히 표시. 연결 안 된 자료도 표시. 상단에 완성도(예: 핵심 결정 30장 중 27장 반영) |
| **인수인계 카드 덱 · 자료** | 공통 | 인수인계 카드와 자료를 보고, 막히면 연결된 업무 기록(과정)으로 내려감. 후임자에게는 인계자가 **공개를 허용한 범위**만 보임 |
| **확인 모드** | 후임자 | 덱의 카드를 한 장씩 넘기며 "이해함 / 질문 있음" 표시. 진행 바가 올라가고(예: 12장 중 8장), 질문 있음 카드는 인계자에게 전달할 **질문 목록**으로 모임 |

### 3-4. 판단 (두 기능이 함께 쓰는 기능)

| 기능 | 내용 |
|---|---|
| **계획 비교** (장면 ①) | "로그 검색용으로 MongoDB 도입해 볼까"를 입력하면 왼쪽에 내 입력 카드, 오른쪽에 관련 카드가 나란히 뜨고 두 카드 사이에 **판정 배지**가 붙음. 기본은 두 종류의 카드를 모두 찾고, 결과 카드에 **"내 기록" / "인수인계" 라벨**이 붙음 |
| **질문하기** | "이 결정은 왜 했지?"에 관련 카드와 원문을 근거로 답하고, 기록에 없으면 "기록에 없음" |

**판정 배지**

| 배지 | 의미 |
|---|---|
| ✅ 일치 | 현재 유효한 결정과 같은 방향 |
| ⚠ 충돌 | 현재 유효한 결정과 반대 방향 |
| 🚫 기각된 안 | 과거에 검토 후 버린 안을 다시 꺼냄 (기각 이유 함께 표시) |
| ➖ 관련 없음 | 해당하는 카드 없음 |

### 3-5. 자료 첨부 (파일 업로드)

업무에서는 자료 파일(예: 학원의 수업 자료)을 그대로 가져다 쓰는 경우가 많아서, **파일을 카드에 연결해 자료와 그 자료의 이유를 함께** 전달합니다.

| 방법 | 내용 |
|---|---|
| **A. 한 화면에서 같이 기록** | 업무 기록 화면에 **파일 드롭존**을 함께 둡니다. 한 번에 올린 로그와 파일은 한 묶음으로 저장되고, 그 묶음에서 생성된 카드에 파일이 연결 후보로 붙습니다. |
| **B. 카드에서 추가** | 카드 상세에서 "자료 추가"로 파일을 첨부합니다. |

- **연결은 자동 제안 + 사람 확인**: 같은 기록 묶음의 파일을 우선 연결 후보로 붙이고, 불확실하면 **"연결 확인 필요"** 로 표시합니다 (기존 "확인 필요"와 같은 방식). 사용자가 수정할 수 있습니다.
- **카드에서** 연결된 자료를 미리보기·다운로드하고, **"자료" 메뉴**에서 파일을 모아 봅니다 (내 업무 / 인수인계 각각).
- **인수인계 점검**에서 "인계할 자료"를 확인합니다 (어느 카드에도 연결되지 않은 파일, 자료가 없는 결정을 빈 자리로 표시).
- **예 (학원)**: 카드 "3주차는 이론보다 실습을 먼저 진행하기로 함 (근거: 지난 학기 설문, 버린 대안: 이론 선행)" + 연결 자료 `3주차_실습자료.pptx` → 후임자가 자료를 그대로 수업에 쓰면서 **왜 이렇게 구성했는지**도 이해합니다.
- **이번 범위**: 업로드, 카드 연결, 미리보기·다운로드. 파일 내용 검색, 로그의 파일 언급 감지, 파일별 한 줄 메모, zip 일괄 업로드는 확장 후보입니다 ([6-7](#6-7-파일-내용-검색-확장-후보) 참고).

### 3-6. 기본 기능과 시각화

| 기능 | 내용 |
|---|---|
| 상태 시각화 | 유효=초록, 폐기=회색 취소선, 대체=새 카드로 이어지는 화살표. 색만으로 구분하지 않고 아이콘과 글자를 함께 씀 |
| 재미 요소(과하지 않게) | 카드가 뒤집히며 생성되는 효과, "확인함" 도장, 완성도 게이지가 차는 변화, 카드 넘기기 |

**일부러 넣지 않는 것**: 점수, 랭킹, 수집 배지 같은 게임 요소
**만들지 않는 기능**: 승인·마감 워크플로우, 슬랙 실시간 연동, 회의 녹음 전사, 권한 관리, 전사 통합 검색, 문서 편집기·뷰어, 프로젝트 선택·관리 화면

### 3-7. 화면 메뉴 구성 (사이드바)

```
홈          대시보드
내 업무      기록하기 · 카드 덱 · 자료
판단        계획 비교 · 질문하기
인수인계     기록하기(인수인계 쓰기)[인계자] · 점검[인계자] · 카드 덱 · 자료 · 확인 모드[후임자]
```

- 인수인계 그룹은 상단의 역할 전환(인계자/후임자)에 맞춰 **해당 역할의 메뉴만** 보입니다. 내 업무는 후임자도 그대로 씁니다.
- 메뉴명은 짧게, 화면 제목은 풀네임으로 구분합니다 (예: "내 업무 기록하기" / "인수인계 쓰기").
- **판단**은 두 영역의 카드를 함께 찾는 기능이라 따로 둡니다.

## 4. 사용 흐름

| 시점 | 사람 | 하는 일 | 화면에서 보는 것 |
|---|---|---|---|
| 평소 | 민준 | 내 업무 > 기록하기: 퇴근 전 업무 대화·메모를 붙여넣고, 관련 자료 파일이 있으면 함께 첨부 | 결정 카드와 과정 타임라인이 자동 생성, 파일은 카드에 연결 후보로 붙음, 확인 필요 카드 표시 |
| 평소 | 민준 | 계획 비교, 질문하기 | 내 과거 결정과 나란히 비교, 🚫 기각된 안 배지, 근거 원문 |
| 이동 전 | 민준 | 인수인계 > 기록하기: 범위를 고르고 AI 초안을 다듬음 | 업무 기록 카드에서 만든 인수인계 카드 초안, 원본 카드 연결 |
| 이동 전 | 민준 | 점검 → 빠진 결정 보강 → 인계 완료 | 빈 자리 카드, 불일치 카드, 완성도 게이지, 덱이 후임에게 넘어감 |
| 인수 후 | 서연 | 인수인계 > 확인 모드: 카드를 한 장씩 넘기며 "이해함 / 질문 있음" | 확인 진행 바, 질문 목록 |
| 업무 중 | 서연 | 하려는 일 입력 (예: "MongoDB 도입해 볼까") | 내 카드와 전임자 카드가 나란히, 🚫 기각된 안 배지 |
| 필요할 때 | 서연 | "이 결정은 왜 했지?" 질문, 인수인계 카드에서 원본 과정으로 내려가기 | 카드와 원문을 근거로 한 답변, 없으면 "기록에 없음" |
| 업무 중 | 서연 | 카드에 연결된 자료(예: 수업 자료)를 열어 업무에 사용 | 카드 상세의 첨부 자료, 미리보기·다운로드 |
| 인수 후 | 서연 | 내 업무 > 기록하기로 자기 업무 기록 | 새 업무 기록 카드 (다음 인수인계의 재료) |

## 5. LLM 설계

한 모델에 모든 일을 맡기지 않고 **역할마다 다른 모델**을 쓰고, 그 선택을 **같은 평가셋으로 비교해서 정합니다.** 아래 모델 계열은 후보이며 최신 버전과 라이선스는 도입 시점에 확인합니다.

### 5-1. 역할별 모델

| 역할 | 모델 | 이유 |
|---|---|---|
| **주력 생성·판정·검증** (판정 설명, **인수인계 카드 초안**, Verifier) | Claude Sonnet 5.5 | 품질과 비용의 균형, 구조화 출력·도구 사용 |
| **대량·저비용 작업** (합성 데이터 일부, 질의 재작성, 보조 분류) | Claude Haiku 5.5 | 호출이 많은 단계의 비용 절감 |
| **교차검증·평가 심사(LLM-as-judge)** | 다른 계열의 API 모델 | 생성 모델과 같은 계열이 심사하면 자기 출력을 후하게 평가하는 편향이 생길 수 있어 분리 |
| **직접 파인튜닝하는 소형 LLM** (결정·과정 추출, 판정) | 소형 오픈 모델(1~8B급, Qwen · Gemma · EXAONE 계열 중 비교 후 선택) | 한국어 성능, 라이선스, Colab에서 QLoRA 가능한 크기 |
| **임베딩** | BGE-M3 계열 등 한국어 임베딩 3종 비교 | 다국어·한국어 지원 |
| **리랭커** | bge-reranker-v2-m3 계열 (Cross-Encoder) | 검색 결과 재정렬 |
| **비교군(baseline)** | KLUE-RoBERTa 등 BERT 계열 분류기 | "LLM 파인튜닝이 정말 이득인가"를 보여주는 기준선 |

### 5-2. LLM Gateway

| 기능 | 내용 |
|---|---|
| 모델 라우팅 | 작업 종류에 따라 Sonnet / Haiku / 로컬 소형 LLM 선택 |
| 재시도·폴백 | 실패하면 재시도, 계속 실패하면 다른 모델로 |
| 구조화 출력 | JSON 스키마를 강제하고 검증 실패 시 자동 재요청 |
| 캐시 | 같은 요청은 재호출하지 않고 비용 절감 |
| 호출 기록 | 모델, 프롬프트 버전, 토큰, 비용, 지연 시간을 `llm_ops` 스키마에 기록 |

### 5-2-1. 작업별 LLM 사용

| 작업 | 모델 | 비고 |
|---|---|---|
| 결정·**과정** 추출 | 파인튜닝 소형 LLM (비교군: Sonnet 5.5 zero-shot, Haiku 5.5, BERT) | 과정 단계(시도·실패·막힘·결정·번복) 분류까지 학습 대상 |
| 판정 | 파인튜닝 소형 LLM + Sonnet 5.5 설명 생성 | |
| **인수인계 카드 초안 생성** | Sonnet 5.5 | 각 문장에 `source_card_ids`를 붙이는 구조화 출력을 강제 |
| 초안·판정 검증 | Sonnet 5.5 또는 다른 계열 | 평가 심사는 생성 모델과 다른 계열 |
| 단계 분류·질의 재작성 | Haiku 5.5 | 호출이 많은 보조 작업 |

### 5-3. LLM 실험 방식 (작은 것부터 → 비교 → 약점 분석 → 개선 → 정량 평가 → 리포트)

| 단계 | 내용 |
|---|---|
| **서비스 니즈에 맞는 지표 선택** | **"기각된 안·충돌" 재현율(recall)이 최우선.** 놓치면 후임자가 이미 기각된 안을 다시 시도하는 것이 가장 치명적입니다. 오탐(잘못된 🚫)은 "확인 필요"와 사용자 수정으로 흡수할 수 있습니다. |
| **후보 모델 5개 비교** | ① Claude Sonnet 5.5 zero-shot ② Haiku 5.5 ③ 다른 계열 API ④ 소형 오픈 LLM 원본 ⑤ BERT 분류기. 같은 평가셋에서 재현율 중심으로 순위를 매김 |
| **CPU vs GPU 속도 비교** | 로컬 임베딩·리랭커·소형 LLM 추론 속도 비교 (서비스에서 어디까지 GPU가 필요한지 판단) |
| **약점 분석 → 파인튜닝** | 1차 평가에서 틀린 사례를 분석(완곡한 기각 표현, 암시적 대안, 여러 번 번복, 긴 스레드)하고 **그런 사례 위주로 학습데이터를 선별**해 소형 LLM을 QLoRA로 파인튜닝. **원본 vs 파인튜닝을 같은 평가셋으로 비교** |
| **전후처리 선정** | 후보를 하나씩 적용하며 효과를 측정(ablation)해 최종 조합 선정 (아래 표) |
| **서빙 최적화·부하 테스트** | 로컬 모델을 vLLM 등으로 서빙하고 응답 시간(p50·p95), 처리량, 호출당 비용 측정 |

| 구분 | 전후처리 후보 |
|---|---|
| **전처리** | 슬랙 말투·이모지·멘션 정규화, 같은 스레드 묶기, 화자·날짜 정규화, 중복·잡담 제거, 긴 스레드 분할 |
| **후처리** | JSON 스키마 검증과 자동 재요청, 근거 없는 판정 강등 규칙, 확신도 임계값 조정, 번복 규칙 보정, 인용이 없으면 거부 |

## 6. RAG 설계

### 6-1. RAG가 쓰이는 곳

| 쓰이는 곳 | 하는 일 |
|---|---|
| **판정 흐름 (Judge)** | 사용자가 입력한 계획과 관련된 과거 카드·기각된 대안을 검색해 일치/충돌/기각/무관을 판정 |
| **카드 기반 질문 (Grounded QA)** | 관련 카드와 원문을 검색해 출처와 함께 답변, 근거가 없으면 거부 |
| **State Linker** | 새 결정이 기존 결정을 번복·대체하는지 판단하기 위해 관련 과거 카드 검색 |
| **Gap Auditor** | 업무 기록 카드와 인수인계 카드를 매칭해 빠진 결정을 찾음 |
| **Handover Drafter** | 인수인계 초안을 만들 때 인계 범위의 업무 기록 카드와 근거 원문을 검색 |

### 6-2. 파이프라인 (AI Agent 안의 6단계)

| 단계 | 내용 |
|---|---|
| ① 질의 재작성 | 짧은 입력("MongoDB 도입해 볼까")을 검색에 맞는 질의로 확장 |
| ② 하이브리드 검색 | 벡터 검색 + 키워드 검색을 함께 사용 |
| ③ 리랭크 | Cross-Encoder로 상위 후보 재정렬 |
| ④ 근거 묶기 | 카드마다 출처 ID를 붙여 프롬프트에 넣음 |
| ⑤ 생성과 인용 검증 | 답변 생성 후 Verifier가 "인용한 근거가 실제로 그 말을 하는가" 확인 |
| ⑥ 거부 | 근거가 충분하지 않으면 "기록에 없음" |

### 6-3. 인덱스 설계 (Allbemi의 특징)

- **인덱스는 하나, 범위는 메타데이터 필터로**: 카드의 `kind`(업무 기록 / 인수인계), `status`, `owner`, `project_id`로 검색 범위를 나눕니다. 계획 비교·질문은 기본 전체, 내 업무 화면은 `kind=work`, 인수인계 화면은 `kind=handover`만 찾습니다.
- **접근 제한은 검색 단계에서**: 다른 사람의 업무 기록 카드는 인계자가 공개를 허용한 경우에만 검색 대상이 되며, 결과를 가린 뒤 거르지 않고 쿼리 필터로 적용합니다. (공개 범위 방식: TODO: 추후결정)
- **과정 단계도 색인**: 시도·실패 문장은 "기각된 안"을 가장 직접적으로 담고 있어 재현율에 유리할 것으로 **가정**하고, R4에서 포함 여부를 비교해 확인합니다.
- **인수인계 카드 → 원본 확장**: 인수인계 카드가 검색되면 `derived_from` 링크로 원본 업무 기록 카드를 함께 가져와 "왜"의 근거로 보여 줍니다. 같은 결정이 두 카드에 있을 때는 인수인계 카드를 우선 표시하고 원본은 접어서 연결합니다. (TODO: 추후결정)
- **두 종류를 따로 색인**: 결정 카드(구조화된 필드별)와 원문 로그 청크(대화 흐름 기준으로 자른 조각). 카드에서 원문으로 이어지는 연결을 유지합니다.
- **폐기·대체된 카드도 검색 대상에 포함**합니다. "기각된 안"을 찾으려면 폐기 카드가 검색에서 빠지면 안 되고, 상태를 메타데이터로 붙여 답변에서 구분합니다.
- **카드 간 관계(`card_links`)로 이웃 확장**: 검색된 카드의 번복·대체 관계를 따라 연결된 카드를 함께 가져옵니다.

### 6-4. RAG 실험 방식 (가장 단순한 baseline → 청킹 다양화 → 고도화 → 정량 평가)

| 단계 | 내용 |
|---|---|
| **R1. baseline** | 원문 로그를 fixed-length로 자르고 가벼운 한국어 임베딩으로 색인, 자연어 검색창에서 유사한 순 5개 표시 (개발용 "RAG Lab". 서비스 프론트엔드에는 넣지 않고 `ml/` 안에서 따로 실행) |
| **R2. 청킹 5종 비교** | fixed 300 · fixed 150 · recursive · semantic · structured(스레드·화자·섹션 구조 기준). 각각 별도 색인하고 **같은 질문의 결과를 한 화면에서 나란히 비교**하는 "Chunking Lab" |
| **R3. 고도화** | ① **제목 임베딩**: 청크마다 한 줄 제목(결정 헤드라인)을 LLM으로 생성해 함께 임베딩, 제목이 검색되면 연결된 원문 청크를 반환 ② **parent-child**: 작은 청크(150자)로 검색하고 그 청크가 속한 논의 구간(스레드 전체)을 반환 ③ **LLM 의미 단위 청킹**: 한 결정이 논의된 대화 구간("결정 에피소드") 단위로 분할 |
| **R4. 정량 평가** | 정성 평가로 고른 청킹 3종 × 한국어 임베딩 3종 = **9케이스**를 평가 |

### 6-5. 평가 질문과 지표

**청크당 질문 3종** (서비스의 실제 사용 방식 반영)

| 질문 유형 | 예 |
|---|---|
| ① 이유를 묻는 질문 | "검색 서버를 왜 Elasticsearch로 정했지?" |
| ② **계획형 질문** (장면 ①과 동일) | "로그 검색용으로 MongoDB 도입해 볼까" |
| ③ 모호하거나 축약된 질문 | "그때 로그 쪽 결정 뭐였지?" |

**지표**: hit rate@k, MRR(정답 순위가 높을수록 점수↑), recall@k, precision@k, nDCG, MAP, 검색 지연 시간, 색인 크기·비용, 그리고 **Allbemi 전용 지표**

| 전용 지표 | 이유 |
|---|---|
| **기각된 대안 검색 재현율** | 폐기·기각된 카드를 찾아내는지가 서비스 핵심 |
| **상태 구분 정확도** | 검색 결과에서 유효·폐기·대체를 올바르게 구분하는지 |
| **parent 반환 적합도** | 부모 구간이 질문에 충분한 맥락을 주는지 |
| 이웃 확장 효과 | `card_links`로 연결 카드를 가져올 때의 개선 |

**평가셋 품질 주의**: 청크에서 질문을 생성하면 청크의 단어를 그대로 베껴 키워드가 겹쳐 점수가 부풀 수 있으므로, 바꿔 말하도록 지시하고 일부를 직접 검수합니다. 학습 데이터와 평가 데이터는 완전히 분리하고 평가셋은 수정하지 않습니다.

### 6-6. 벡터 DB

| 선택 | 장점 | 단점 |
|---|---|---|
| **랩은 Chroma, 서비스는 pgvector** (현재 추천) | 실험이 빠르고 서비스는 DB 하나로 단순 | 승격할 때 옮기는 작업 |
| 처음부터 pgvector만 | 한 번에 통일 | 실험용 컬렉션을 여러 개 만들 때 약간 번거로움 |

### 6-7. 파일 내용 검색 (확장 후보)

이번 범위(3-5)는 파일을 카드에 연결하는 것까지입니다. 일정에 여유가 있으면 파일 내용도 RAG에 넣습니다.

| 확장 후보 | 내용 |
|---|---|
| 텍스트 추출 + 구조 기반 청킹 | PDF·PPTX 등에서 텍스트를 추출하고 슬라이드·페이지·섹션 단위로 청킹 (Chunking Lab에 "파일 구조 기반" 방식 추가) |
| 검색·인용 | 로그 청크와 같은 인덱스에 `source_type=file`로 저장하고, 답변에서 파일명과 슬라이드·페이지 번호를 인용 |
| 로그의 파일 언급 감지 | "3주차 자료 수정했어요" 같은 문장이 있는데 첨부가 없으면 "관련 파일을 첨부할까요?" 제안 |
| 파일별 한 줄 메모, zip 일괄 업로드 | 자료의 이유를 짧게 남기기, 자료 폴더를 한 번에 올리기 |

텍스트가 없는 스캔본·이미지는 OCR이 필요해서 이후 단계입니다. 파일은 **카드와 연결된 범위 안에서만** 검색하고, 전사 통합 검색은 만들지 않습니다.

## 7. 에이전트 평가

- **LLM-as-judge**로 평가하되, **생성 모델과 다른 계열**을 쓰고 일부는 사람이 검수해 심사 모델과의 일치도를 확인합니다.
- 일반적으로 쓰는 에이전트 평가 지표를 조사한 뒤 서비스에 맞는 지표를 선정합니다. 도구는 ragas · LangChain 평가 도구를 기본으로 하고, 고유 지표는 직접 구현합니다. (한국어에서 점수가 안정적인지 확인 필요)

| 지표 | 의미 |
|---|---|
| **판정 정확도** | 4분류(일치·충돌·기각·무관) macro-F1, **기각·충돌 재현율(핵심)** |
| 라우팅 정확도 | Supervisor가 요청에 맞는 흐름(기록·판정·점검·확인)을 골랐는가 |
| **인용 정확도·충실도** | 답변이 실제 근거에 기반하는가 |
| **거부 정확도** | 기록에 없는 질문에 "기록에 없음"이라고 답하는가 |
| **확신도 보정** | "확인 필요"로 표시한 카드가 실제로 틀릴 가능성이 높은가 |
| 단계 효율 | 호출 횟수, 지연 시간, 비용 |
| Verifier 효과 | Verifier 유무에 따른 환각률 차이 |
| **과정 추출 정확도** | 단계 경계와 유형(시도·실패·막힘·결정·번복) 일치도 |
| **인수인계 초안 충실도·누락률** | 초안 문장 중 원본 카드로 뒷받침되는 비율, 핵심 결정 중 빠진 비율 (LLM-as-judge + 사람 검수) |
| **Gap Auditor 재현율** | 일부러 빼 둔 결정(심어 둔 빈 자리)을 찾아내는 비율 |
| 범위별 검색 정확도 | 내 업무 / 인수인계 / 전체 범위에서 정답 카드를 찾는지, 접근 제한이 지켜지는지 |

### 평가 데이터셋

| 데이터셋 | 만드는 방법 | 용도 |
|---|---|---|
| **결정 레코드(정답)** | 가상 회사 프로젝트 3개, 약 100개를 직접 구조화 (번복·기각 관계, **과정 단계, 인수인계 초안 정답** 포함) | 모든 평가의 기준 |
| **로그 코퍼스** | 결정 레코드에서 LLM이 슬랙 대화체로 생성 (잡담·모호한 표현 포함), 일부 검수 | RAG 색인 대상, 추출 평가 |
| **RAG 평가 질문** | 청크당 질문 3종을 LLM이 생성 | 검색 평가 |
| **판정 평가셋** | 같은 레코드에서 (계획, 카드) 쌍을 4가지 관계로 생성, 일부 직접 검수 | 판정 모델 평가·파인튜닝 |
| **소량 실제 대화** | 지인·동료의 익명화된 업무 대화 몇 건 | 합성 데이터 한계 검증 |

**측정하지 않은 수치는 쓰지 않습니다.**

## 9. 시스템 구조

![올빼미 구조도](docs/architecture/Allbemi_architecture.png)

- **Docker Compose 서비스 5개, 외부 공개 포트는 8080 하나**: Frontend(:8080) → Backend(:8000) → AI Agent(:8100) → LLM Gateway(:8300) / Model Server(:8200)
- **DB**: PostgreSQL + pgvector, 스키마 3개. `app`(Backend만 쓰기, 사용자·업로드·**인수인계 묶음과 확인 표시**·**첨부 파일 정보**), `memory`(Agent만 쓰기, 카드·벡터·판정·실행 기록), `llm_ops`(LLM Gateway만 쓰기, 호출 기록·캐시). Backend는 `memory`를 읽기 전용으로만 접근합니다.
- **외부**: LLM API(주력), LLM API(교차검증·심사), [선택] Langfuse
- **오프라인(Compose 밖)**: 합성 데이터 생성기, QLoRA 파인튜닝, 평가 하네스·CI
- **파일 업로드**: Backend가 업로드를 받아 형식·크기를 검증하고, 파일 본체는 별도 볼륨(`allbemi-files`)에, 파일 정보와 카드 연결(`files`, `card_files`)은 `app` 스키마에 저장합니다. 업로드한 파일은 실행하지 않고 저장만 합니다.
- 호출은 한 방향이고, 판정 규칙·prompts는 엔진 코드에 하드코딩하지 않고 `packs/work/`에서 로드합니다.

### 멀티 에이전트 (LangGraph)

| 흐름 | 에이전트 |
|---|---|
| 총괄 | Supervisor (업무 기록 / 인수인계 초안 / 판정 / 점검 / 확인 / 질의로 라우팅) |
| 업무 기록 | Extractor(결정 + 과정) → State Linker → Confidence Gate (확신 낮으면 사람 확인) |
| **인수인계 초안** | **Handover Drafter → Verifier** (모든 문장이 원본 카드에 근거하는지 확인) |
| 판정 | Intent Parser → Retriever/Reranker → Judge → Verifier |
| 점검 | Gap Auditor (업무 기록 카드 vs 인수인계 카드) |
| 확인 | Question Drafter |
| 질의 | Grounded QA (두 종류 카드 모두, 근거 없으면 거부) |

### 기술 스택 (제안)

FastAPI, LangGraph(+LangChain), PostgreSQL + pgvector, Chroma(RAG Lab), React 계열 프론트, PyTorch/Transformers + PEFT(QLoRA), vLLM, BGE-M3 계열, Cross-Encoder, ragas, Langfuse, Docker Compose, GitHub Actions

## 10. 프론트엔드 목업 범위 (진행 중)

서버 없이 가짜 데이터(mock)만으로 동작하게 합니다. 화면은 사이드바(3-7) 구성과 맞춥니다.

| 화면 | 메뉴 | 포함 내용 | 우선순위 |
|---|---|---|---|
| **A. 카드 덱** | 내 업무 / 인수인계 > 카드 덱 | 상태별 색, 시간순 정렬, 프로젝트 이름표, 카드 상세(원문 펼치기, 버린 대안, **과정 타임라인**, 인수인계 카드는 원본 카드 링크, 첨부 자료 미리보기·다운로드) | 필수 |
| **B. 계획 비교** | 판단 > 계획 비교 | 입력창, 내 입력 카드와 관련 카드 나란히, 판정 배지 4종, 기각 이유, "내 기록/인수인계" 라벨 | **필수 (최우선)** |
| **C. 내 업무 기록하기** | 내 업무 > 기록하기 | 붙여넣기 영역, **파일 드롭존**, 카드가 뒤집히며 생성, 과정 타임라인, "연결 확인 필요" 표시, 수정 | 필수 |
| **D. 카드 상태 시각화** | 카드 덱 안 | 유효/폐기/대체 표시, 대체 화살표 | 필수 |
| **E. 인수인계 쓰기** | 인수인계 > 기록하기 | 범위 선택, AI 초안 카드(원본 카드 연결), 다듬기, 인수자 메모 | 필수 |
| **F. 인수인계 점검** | 인수인계 > 점검 | 빈 자리 카드, 불일치 카드 나란히, 완성도 게이지, "인계할 자료" | 선택 |
| **G. 확인 모드** | 인수인계 > 확인 모드 | 카드 한 장씩 넘기기, 이해함/질문 있음, 진행 바, 질문 목록 | 선택 |
| **H. 질문하기** | 판단 > 질문하기 | 카드 기반 답변, "기록에 없음" 응답 | 선택 |
| **I. 자료** | 내 업무 / 인수인계 > 자료 | 파일 표, 형식 필터, 연결 안 된 파일, 미리보기 | 필수 |
| **J. 대시보드** | 홈 | 확인할 일, 카드 상태 요약, 최근 결정과 판정, 인수인계 진행 | 선택 |

**개발용 화면은 서비스 프론트엔드에 넣지 않습니다.** RAG Lab / Chunking Lab은 `ml/` 안의 별도 도구로 두고 실험 결과는 리포트(`eval/reports/`)로 남깁니다.

**목업용 가짜 데이터**: 가상 프로젝트 2개, 카드 15~20장(유효/폐기/대체/확인 필요가 섞이게, 업무 기록 카드와 인수인계 카드 포함, 과정 단계 포함), 판정 예시(일치·충돌·기각·무관 각 1개 이상). MongoDB 도입 시나리오를 중심에 둡니다.

## 11. 사용자에게 주는 이점

| 사용자 | 이점 |
|---|---|
| **나 (평소)** | 형식 없이 붙여넣기만 해도 결정과 과정이 남음, 내가 이미 기각한 안을 다시 꺼내면 알려 줌, "내가 왜 그랬지"를 근거 원문으로 확인 |
| **인계자** | 인수인계를 처음부터 쓰지 않고 AI 초안에서 시작, 점검으로 빠진 결정과 완성도 확인, 근거와 버린 대안까지 전달 |
| **후임자** | 기각된 안을 먼저 알려 줘서 시행착오 방지, 두 카드 비교로 빠른 파악, 막히면 원본 과정까지 확인, 없으면 "기록에 없음", **자료 파일을 이유와 함께 받아 바로 업무에 사용** |
| **팀** | 사람이 떠나도 이유가 남음, 번복된 결정을 현행으로 오해하지 않음, 인수인계 시간 단축 |

| 직접 설계·판단 | 기술 선택마다 이유를 기록하고, **개발 결정을 Allbemi 자체에 기록하는 도그푸딩** |

**절대 자르지 않는 것**: 장면 ①, 업무 기록 → 인수인계 초안으로 이어지는 흐름, 평가셋, RAG 정량 평가(R4), 모델 비교(A1)

## 14. 리스크와 한계

- 자동 생성과 판정은 **제안이며 틀릴 수 있습니다.** 확신이 낮으면 "확인 필요"로 표시하고 사용자가 수정하거나 무시할 수 있어야 합니다.
- **기록이 없는 결정은 알 수 없습니다.** 평소 로그를 넣어야 쓸모가 생긴다는 한계를 전제로 합니다.
- 합성 데이터는 실제 업무 대화보다 정돈되어 있어 실제 환경 성능은 별도 검증이 필요합니다. 평가 질문을 청크에서 생성하면 키워드가 겹쳐 점수가 부풀 수 있습니다.
- **GPU와 API 비용**: 파인튜닝·속도 비교에는 GPU가, 합성 데이터·질문 생성·LLM-as-judge에는 많은 API 호출이 필요합니다. 환경에 따라 모델 크기와 실험 범위를 조정합니다.
- **파일 업로드의 위험**: 자료에는 저작권이나 개인정보가 들어 있을 수 있어 **공개 저장소와 데모에는 합성 자료(가상 수업 자료)만** 사용합니다. 업로드 파일은 형식·크기를 검증하고 실행하지 않고 저장만 합니다 (바이러스 검사는 이후 단계). 파일과 카드의 자동 연결은 틀릴 수 있어 "연결 확인 필요"로 표시합니다.
- **과정 추출은 결정 추출보다 어렵습니다.** 단계 경계와 유형 라벨이 모호해 평가셋 주석 비용이 늘고, 정확도가 낮을 수 있어 "확인 필요"와 사용자 수정을 전제로 합니다.
- **인수인계 초안은 환각 위험이 있습니다.** 모든 문장에 원본 카드를 연결하고 Verifier로 검증하며, 최종 책임은 인계자의 확인에 둡니다.
- **후임자에게 업무 기록(개인 메모)이 노출될 수 있습니다.** 공개 범위를 인계자가 정하게 하고, 공개 저장소·데모에는 합성 데이터만 씁니다.
- 1인 6주에 범위가 크므로 얇은 버전부터 완성하고, 자르는 순서를 미리 정해 둡니다.

## 15. 아직 정해지지 않은 것

1. ~~프론트엔드 기술~~ → React + Vite + TypeScript + Tailwind로 목업 진행 중 (확정)
2. 레포 구조 (모노레포 유지 vs 분리) — 보류
3. GPU 환경(Colab 포함), LLM API 월 예산
4. 벡터 DB 전략 (랩 Chroma → 서비스 pgvector 이관 여부)
5. 소형 오픈 LLM 후보 확정, 한국어 임베딩 3종 선정
6. 수업 제출 형식, 서비스명 "Allbemi"의 도메인·상표 중복 확인
7. 지원할 파일 형식(PPTX·PDF 우선 검토)과 파일 저장 방식, 업로드 크기 제한
8. **업무 기록 카드의 "과정" 범위**: 결정 카드에 붙는 타임라인까지(현재 가정)인지, 하루 업무 일지 전체인지
9. **후임자의 업무 기록 열람 방식**: 인계자가 카드별로 공개를 허용할지, 인계 범위 전체를 공개할지
10. **같은 결정이 두 카드에 있을 때의 표시**: 인수인계 카드를 우선 표시하고 원본을 접어서 연결(현재 가정)할지

## 폴더 구조

| 폴더 | 역할 |
|---|---|
| `frontend/` | 카드 화면 (내 업무 / 인수인계 / 판단, 카드 비교, 상태 시각화, 완성도 게이지, 확인 모드) |
| `backend/` | API, 인증, 카드 CRUD, 인수인계 묶음·확인 표시, 로그·파일 업로드 |
| `agent/` | LangGraph 멀티 에이전트와 RAG 파이프라인 |
| `model-server/` | 임베딩, 리랭커, 파인튜닝 소형 LLM 서빙 |
| `packs/work/` | 결정 스키마 · 판정 규칙 · prompts (엔진과 분리된 도메인 설정) |
| `contracts/` | 서비스 간 유일한 약속 (API, DB, 결정 카드 형식) |
| `ml/` | 합성 데이터 생성, 모델 학습, RAG Lab (개발용 도구) |
| `eval/` | 평가 하네스, 지표, 기준선, 고정 평가 세트, 리포트 |
| `data/` | 생성된 샘플·합성 데이터 |
| `libs/common/` | 공통 코드 |
| `infra/` | docker-compose, Dockerfile |
| `scripts/` | 로컬 실행·시드 스크립트 |
| `docs/` | 기획, 결정 기록, 구조도 |
| `.claude/`, `.github/` | 개발 자동화, CI |

구조 원칙: 호출 방향은 **Frontend → Backend → Agent → LLM Gateway / Model Server** 한 방향, DB 스키마마다 쓰기 주체는 하나, 판정 규칙·prompts는 `packs/work/`에서 로드, 평가 세트와 기준선은 학습 데이터와 분리하고 수정하지 않음. (LLM Gateway 서비스를 위한 폴더는 구현 시점에 추가합니다.)
